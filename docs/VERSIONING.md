# 版本与发布规范

从 0.1.0 之后开始严格按语义化版本（SemVer）打标签、推送。

## 版本号怎么涨

| 改动 | 版本 | 例子 |
|---|---|---|
| 修 bug、文档、兼容层清理、性能优化（不改对外行为） | **patch** `0.1.x` | 0.1.1 → 0.1.2 |
| 加功能、加配置项、加能力（行为有新增，但旧用法不破） | **minor** `0.x.0` | 0.1.x → 0.2.0 |
| 破坏性改动（删旧路径、改数据格式、配置不兼容） | 0.x 阶段用 minor 表达，并在发布说明里写明迁移 | 0.2.0 → 0.3.0 |

0.x 阶段不做 1.0.0，直到满足：数据格式稳定、旧兼容层删干净、真机验证过一轮完整生活周期。

## 一次改动的固定流程

```powershell
# 1) 改代码 + 测试全绿（分层检查也在里面）
npm run test:all
npm run smoke

# 2) 提交（一个改动一个提交，信息写清楚修了什么）
git add -A
git commit -m "fix(ui): 住处页在没住处时显示未分配，而不是空白"

# 3) 打标签（下面是 0.1.1 的例子）
git tag -a 0.1.1 -m "0.1.1: 住处页空白修复"

# 4) 推送（代理不通就直连）
$url = "https://<token>@github.com/fandreamfish/fishbowl.git"
git -c http.proxy=http://127.0.0.1:7892 -c https.proxy=http://127.0.0.1:7892 push $url HEAD:main
git -c http.proxy=http://127.0.0.1:7892 -c https.proxy=http://127.0.0.1:7892 push $url refs/tags/0.1.1

# 5) 更新进度列表（ROADMAP + GitHub 主页）和本次发布说明
```

## 发布说明

- 每次打标签都写 `docs/releases/<version>.md`（一句话结论 + 改了什么 + 迁移注意事项）
- 0.1.0 是例外，说明在 `docs/RELEASE-0.1.0.md`
- 标签必须推到远程；本地打标签不推等于没发布

## 什么不算 patch

- 只改注释、只改格式：不单独发版，跟下一个改动一起
- 只改测试：不单独发版（除非测试暴露了真实 bug）
