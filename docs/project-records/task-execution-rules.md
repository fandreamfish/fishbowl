# Fish 外部任务执行规则

状态：2026-11-03 用户确认采用推荐方案。本文是当前任务执行规则；早期文档与本文冲突时以本文为准。仅确认需求与边界，未实现或验证 DSH 接口。

补充状态：基础 API 探针证据见 [dsh-task-validation.md](dsh-task-validation.md)，不代表完整接入已通过。[任务协议](task-protocol-design.md) 和 [插件状态机](dsh-control-state-machine.md) 已形成待评审草案；草案中的具体参数和技术取舍不覆盖本文已确认规则。

## 1. 能力与 Agent 边界

Fish 拥有独立的模型、上下文、记忆、工具选择和任务编排能力。QQ 消息对接与 DSH 操作是两项独立能力，按需组合，不构成固定转发管道。

Fish 自己的 Agent 循环负责理解消息、选择能力、提交任务和处理结果；DSH 自己的 Agent 循环负责执行被委托的任务。DSH 自主管理执行，不意味着 Fish 的独立 Agent 能力后置或取消。

DSH 插件主动连接 Fish，首选 WebSocket。建连方向与任务调用方向分开；本地可使用等价 IPC，远程连接需要认证和加密。

## 2. 项目与会话选择

调用携带已授权的项目标识，由 DSH 插件映射到本机工作区，不把消息中的任意路径当作授权依据。目标缺失或有歧义时先澄清，不猜测执行项目。

首期复用该鱼绑定的 DSH 执行会话，保持每鱼每类一个接入、每鱼一个 DSH 会话、每 DSH 会话一条鱼的约束。会话尚未配置时先完成绑定；不默认按每个任务新建会话。以后扩展多项目或多会话时另行定义映射规则。

## 3. 任务协议与结果

Fish 发送任务 ID、关联 trace、发起者、入口回复目标、已授权项目标识和任务要求。协议字段和 Schema 在后续设计中冻结。

DSH 可返回接收确认或拒绝；允许连接心跳、任务查询及取消确认等控制消息。Fish 不订阅 DSH 内部思考、模型调用、工具调用和执行进度。连接在线不证明某个任务执行正常。

DSH 负责判定执行结束，并回传成功、失败或取消等明确终态。无法确定是否执行或是否完成时，应明确报告结果未知，不能伪装为失败、成功或取消；结果未知可在后续核对后被确定结果更新。

最终结果至少关联任务 ID，包含终态、结果说明、错误（适用时）和必要产物引用。代码任务应说明修改文件、测试执行情况及其结果；未运行测试必须明确标注。DSH 返回的成功是执行端报告，Fish 不据此声称已独立验证。

Fish 按结果决定继续编排或回复原请求者；后续调用使用新的任务 ID，保留原任务关联，不把新工作混作同一任务重试。

### 需要用户补充信息（已确认）

DSH 无法继续且需要用户提供信息时，以“需要补充信息”（needs_input）结束本次任务，返回具体问题、所需信息和已经产生的影响，不无限占用执行任务等待用户。该状态表示本次任务已结束但目标尚未完成，不属于成功。

Fish 将问题发送给原请求者；用户补充后，Fish 保留原任务、问题和用户答复的关联，使用新的任务 ID 提交后续任务。新任务明确已完成的操作和剩余目标，避免重复副作用；不能只把用户答复作为无上下文的新指令。原任务不重新打开，未答复时不自动续跑。

这是最终结果的一种，不要求回传 DSH 内部过程。敏感问题仍遵守披露策略；此机制不用于绕过 DSH 工具审批。

## 4. 异步执行与队列

Fish 持久化任务和 DSH 接收确认后，可以结束当前消息回合，告知用户任务已提交，并继续聊天。等待 DSH 不长期占用该鱼消息队列。未收到确认时不得声称已接收。

同一条鱼的消息回合仍串行执行；DSH 最终结果作为独立事件进入该鱼统一队列，由 Runtime 串行写入状态和记忆，不能由外部回调并发改账。用户消息优先于鱼间消息；结果事件须得到处理，防饥饿细节留待调度设计。

首期同一 DSH 执行会话串行处理委托任务，后续任务排队，不默认打断当前任务。不同鱼按各自绑定独立运行。用户提出依赖进行中任务的后续工作时，保留任务关联，不将其作为无关任务并行执行。

任务结束后向原请求者和原渠道通知；该渠道不可用时持久化待投递结果并在恢复后补发，不将私密结果自动改发其他对象或群聊。

## 5. 幂等、断线与取消

任务 ID 在首次提交前持久化。同一 ID 重复提交不得重复执行；相同 ID 对应不同请求内容必须拒绝。DSH 插件/执行端持久化任务映射、接收和最终结果以支持去重及恢复。

断线、响应丢失或 Fish 等待超时不意味着 DSH 停止或失败。DSH 已接收的任务由 DSH 继续掌控，完成后保存结果，重连后按任务 ID 查询或补投；副作用状态未知时不盲目重新执行。

Fish 重启后恢复待处理任务和通知；DSH 重启后先核对本地记录，不确定的任务标记为结果未知。最终结果投递需要确认与去重，重复回传不重复记账或通知；确认前保留可重投结果。

取消是一项独立控制请求。Fish 发出取消不等于 DSH 已取消，必须等待 DSH 确认。取消或超时不撤销已经完成的文件修改或其他外部操作；最终结果说明已产生的影响。具体超时值和保留期限待协议设计确定。

## 6. 授权和审批

以真实渠道身份判断谁能调用 DSH；按用户、鱼、能力和项目授权，接入 QQ 本身不授予 DSH 操作权限。群聊中被 @、转发的指令或聊天文本不等于管理员授权。

DSH 插件执行入口校验认证、权限和项目。DSH 内部工具审批由 DSH 自身机制处理，不通过 Fish 逐步审批或绕过限制。无法获得必要审批时，按 DSH 策略结束并返回明确错误及已完成影响，避免无限等待。

## 7. 审计、状态和记忆

Fish 记录自身模型/编排活动，以及任务请求、权限判断、提交、接收确认、取消、最终结果和通知，使用统一任务 ID 与 trace 关联。

DSH 保存内部执行记录及审计，Fish 不接收这些内部记录。可通过任务 ID 供管理员跨两端核对；全链路可追溯不要求将 DSH 内部事件复制进 Fish。两端分别持有自身状态，DSH 不直接写 Fish 账本。

记忆记录用户委托内容和 DSH 返回的最终结果，标注 DSH 来源及成功、失败或未知状态。不能把 DSH 内部工作记成 Fish 亲自执行或亲眼观察，也不把执行端返回内容当作新的用户授权或系统指令。结果按当前对象的披露规则发送。

## 8. 首期验收与后续设计

- QQ 能单独与 Fish 聊天，不自动调用 DSH；DSH 能力不限定由 QQ 触发。
- 在授权项目中提交一次代码任务，DSH 自主执行，Fish 只收到控制确认和最终结果。
- DSH 执行期间 Fish 可以处理新消息，结果回到原请求者并进入记忆。
- 重复提交、重复结果、断线重连和两端重启不导致重复副作用或重复记账。
- 验证失败、拒绝、审批不可用、结果未知及取消竞态，不将超时当作成功取消。
- 两端按任务 ID 可核对审计；Fish 不保存 DSH 中间执行内容。

待设计：DSH 当前版提交/完成/取消 API 的真实可行性、消息 Schema、认证机制、具体配额/超时/保留值、调度防饥饿与结果产物传输。首期不要求模型拦截、外部 assistant 回灌或 DSH 内部过程流式回传。
