# 通道设计：QQ / B 站（M3.1 设计稿，M3.3 实施）

> 本体只有一个，通道是多张"嘴"。每条通道有场合（register）与披露边界。

## 通道表（已入代码 `src/core/channels.ts`）

| 通道 | 场合 | 注入的记忆 | 说明 |
|---|---|---|---|
| DSH 会话 | intimate | 全部 | 主通道，只有你 |
| QQ 私聊 | intimate | 全部 | 一对一，同 DSH |
| QQ 群 | public | **无** | 公开场合：没有"我们的记忆" |
| B 站评论 | public | **无** | 公开表达：只发"她想说的"，不带关系记忆 |

## 披露边界（硬规则）

- **私聊里的记忆不能在群里被引用**——公开通道的注入里没有语义、教训、承诺，只有她的状态与声音
- B 站评论的内容来源：她的议程与情绪（"想说的"），而不是关于你们的关系

## QQ 适配器（M3.3 实施）

**两条路**：

| 路线 | 形态 | 风险 |
|---|---|---|
| 官方 QQ 开放平台 | HTTP Webhook / WebSocket | 稳、需认证；**主动私聊有限制，需先查清当前策略** |
| OneBot 实现（NapCat 等） | 本地 HTTP / WS 长连接 | 灵活、门槛低；**非官方协议，有封号风险** |

**架构**：

```
fishbowl 插件（DSH 内）
   └─ channel-qq 子模块：OneBot/官方 API 客户端
        入：收到私聊/群消息 → 组装事件 → 复用 collector 的 pipeline
        出：她想主动说话 → 按 channel 场合过滤记忆 → 发消息
```

**实施时先查清三件事**（上一轮已列，仍有效）：

1. 官方对"主动私聊"的限制（可能比我们的配额更严）
2. OneBot 的 HTTP 事件与发送接口
3. 群消息的"要不要回应"策略（@她 / 关键词 / 频率）

## B 站适配器（M3.3+）

- 评论 = 公开场合：内容只来自她的议程（§10 自我议程，M3 后实现）或当前情绪的自然外化
- 需要先有"她想说什么"的来源——议程层，这是 M3.3 与议程层一起做的原因
- 观看/一起看视频：工具层（拿到视频信息 → 会话内聊），不依赖 B 站 API 的评论能力

## 投递队列（已实现，M3.1）

会话没开着时她想说的话不会丢：

```
creatures/<id>/outbox.json
  [{ id, ts, text, channel, delivered }]
```

- 幂等：id 去重；at-least-once：投递成功后标记
- 会话重开（agent/created）时补投，失败下轮再试
- 积压合并（多天未读合成一条）留给 M3.2
